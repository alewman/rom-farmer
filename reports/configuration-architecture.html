📋 Executive Summary

ROM Farmer uses a layered configuration architecture that separates concerns across multiple levels. This document analyzes the current architecture, identifies gaps, and proposes enhancements to support target-specific capabilities.

Key Insight: Targets currently have no identity. They exist only as names with output paths. The system cannot answer questions like "Does RocknIX support PDF manuals?" or "What folder name does RocknIX use for Sega CD?"

⚠️ Current Limitations

Problem 1: Target Capabilities Unknown

The system has no way to know what a target can or cannot do.

// Current: Hardcoded check buried in metadata.py
if context.target_name == 'rocknix' and media_type == 'manual':
    continue  // Skip manuals for RocknIX
Issues: Hardcoded logic scattered throughout codebase. Adding new targets requires code changes.

Problem 2: Platform-Target Constraints Missing

The system can't prevent impossible combinations.

// This will fail at runtime, not at config validation:
platforms:
  - ps3
targets:
  - name: rocknix  // RocknIX can't emulate PS3!
Issues: No early validation. Wasted processing time. Confusing errors.

Problem 3: Folder Name Mapping Fragmented

Different targets use different folder names.

InternalBatoceraRocknIX
megacdmegacdsegacd
pspminispsp/pspminispspminis
Workaround: platform_folder_map duplicated across builds

Problem 4: Compression Fallback Missing

If a target doesn't support 7z, the build produces unusable output.

Current: No validation or fallback
Needed: Automatic fallback (7z → zip)

Target Definition Schema

❌ Current: RocknIX (Inline)

// Inside platform config
targets:
  - name: rocknix
    output_path: /path/to/output/rocknix/saturn
    organization:
      style: balanced
    metadata: true

No capabilities defined!

✅ Proposed: RocknIX Target File

// config/targets/rocknix.yaml
name: rocknix

media_support:
  - image
  - mix
  - wheel
  - video
  // NO manual - no PDF viewer

compression_support:
  - zip
  - chd
  - cso
  // NO 7z

compression_fallback:
  7z: zip

platform_support:
  - nes
  - snes
  - psx
  // NO ps3, xbox360

folder_mapping:
  megacd: segacd

📋 Implementation Priority

  • Phase 1: Target Definition Files (High Priority)
    Create the target definition layer with media support and platform support.
    • Create Pydantic models for target definitions
    • Create config/targets/batocera.yaml
    • Create config/targets/rocknix.yaml
    • Create target loader
    • Wire into metadata stage
    • Add platform support validation
  • Phase 2: Compression Handling (Medium Priority)
    Add compression support and fallback logic.
    • Add compression_support to target schema
    • Add compression_fallback mapping
    • Wire into compression stage
    • Add validation warnings
  • Phase 3: Folder Mapping (Medium Priority)
    Centralize folder name mapping in targets.
    • Add folder_mapping to target schema
    • Wire into organize stage
    • Remove platform_folder_map from builds
    • Migrate existing configs
  • Phase 4: Platform Capabilities (Lower Priority)
    Formalize platform hardware capabilities.
    • Add capabilities section to platform schema
    • Rename multi_disc_handling to capabilities.disc_swap
    • Migrate existing platform configs
    • Document capability patterns

  - nes
  - snes

🎯 Declarative

Capabilities declared in YAML instead of scattered hardcoded checks throughout the codebase.

⚡ Early Validation

Impossible combinations caught at config load time, not after hours of processing.

🔄 Centralized

Folder mappings defined once in target files, not duplicated across every build.

📚 Self-Documenting

Target files serve as documentation of what each device supports.

Summary

The proposed architecture introduces a first-class Target layer that declares capabilities instead of scattering hardcoded checks, validates early instead of failing at runtime, centralizes mappings instead of duplicating across builds, enables fallbacks instead of producing unusable output, and documents constraints as code instead of tribal knowledge.

This is foundational work that will make ROM Farmer more maintainable, extensible, and user-friendly.
